## New Breakage in the Fix Diff

**Minor 1 — `delete_points` can leave the layer's contour list empty on an error return.**
`crates/fw-doc/src/command/outline/delete.rs:46` moves the contours out with `std::mem::take(&mut target.contours)` into a local, and the loop body then propagates with `?` (`:54` `keep_shape`, `:57` `break_at_points`; reachable via `Error::InvalidCommand("handle has no preceding node")` at `delete.rs:181/183/409/411/450/452`). On that path the function returns while `target.contours` is still the empty vec left by the take. It is invisible today only because `Restore::capture` routes `DeletePoints` to the whole-layer arm (`outline.rs:117`). The coupling is undocumented and one-directional: narrowing `DeletePoints`' capture later, or calling `delete_points` from anywhere other than `outline::apply`, silently empties the glyph. Suggest putting `source` back on the error path (or a comment at the take tying it to the whole-layer capture).

**Minor 2 — the new doc comment on `outline::apply` overstates the preview win.**
`crates/fw-doc/src/command/outline.rs:150-152` claims the narrow capture "keeps a preview frame proportional to the selection rather than to the glyph". It does not: `Document::apply_command` — which `preview_edit` reaches through `apply_in_edit` (`crates/fw-doc/src/edit.rs:11`, `crates/fw-doc/src/document.rs:163`) — still performs two full `Glyph` clones per frame (`document.rs:312`, `:322` → `undo.rs:199-203`), covering every layer of the glyph including the background image bytes the comment says are no longer copied. The saving is real (one layer clone per frame) but is not the dominant term, and the doc comment and report item 4 both assert a property the crate does not have. Reword to "captures only the parts it names" without the asymptotic claim.

**Minor 3 — the declared format is import provenance, so it never follows a user's curve conversion.**
`crates/fw-model/src/query/curves.rs:35` reads `font.extra.source.table_tags`, which is written once at import and never updated. After `PathOp::ConvertCurves(CurveKind::Cubic)` on an imported TTF the font still declares Quadratic, so `ConvertSegment { to: Curve }` inserts a single `QCurve` control into a now-cubic contour (`segments.rs:99` → `:131`) and `DeletePoints` fits quadratic spans (`delete.rs:36`); the mirror case (imported OTF converted to quadratic) gets cubic handles. The old contour heuristic handled both correctly. Nothing becomes malformed — mixed contours are legal and `try_to_bezpath` accepts them — so this is Minor, and it follows the dispatch's binding "font wins over layer" ruling; but the ruling assumed a declared outline *kind*, not immutable provenance. Follow-up: have `ConvertCurves` record the resulting format, or ignore the declaration when the layer's outlines uniformly contradict it.

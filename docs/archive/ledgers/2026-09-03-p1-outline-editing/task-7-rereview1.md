### New Breakage in the Fix Diff

1. **Minor — state is cleared but the canvas is not told, in two places the fix created.** (a) `route()` calls `gestureEnded` *after* `consume()` has already repainted (`toolHost.ts:235-238`) and `gestureEnded` only does `this.snapping.clear()` with no repaint (`editorController.ts:147`), so the halo pixels survive the gesture end until the next paint. (b) The m12 gating removed the unconditional repaint that used to follow a tool switch: `ToolHost.setTool` → `finishCurrent()` → `consume(tool.finish(...))` (`toolHost.ts:160-164`, `:221-226`), and `MeasureTool.finish()` returns `NO_OUTCOME` (`tools/measure.ts:102-108`), as does `PenTool.finish()` for a one-node path; `EditorController.setTool` does not repaint either (`editorController.ts:224-229`) and `GlyphCanvas`'s repaint effect has no `tool` dependency (`app/src/views/glyph/GlyphCanvas.tsx:289-299`). So switching away from Measure leaves the measurement painted until something else repaints. In practice the next pointer move fixes both; with a stationary pointer and a keyboard tool switch they are visible. One `repaint()` in `gestureEnded` and one in `setTool` closes it.

2. **Minor — a nudge started during a live drag loses its optimistic preview one tick later.** The m6 fix makes `nudgeSelection` settle the drag first (`editorController.ts:525`), but `finishDrag`'s `finally` does an unconditional `this.setPreview(null)` (`editorController.ts:788-791`) — unlike `closeNudge`, which deliberately guards on `this.drag` for exactly this reason (`:591-598`). The nudge's preview is installed synchronously at `:527`, then wiped when the drag's `finish()` resolves, so the nudged points snap back until the kernel round trip lands. The transport sequence is correct (the ruled test passes); this is a preview-only artefact of the same kind I2 was about.

3. **Minor — `curveFit.ts` is 538 lines, over ruling 14's 450-line soft cap for a new module** (hard cap 800 is respected). The first review's "every new module is ≤ 450 lines" no longer holds and the report does not list it as a deviation. The file splits cleanly (fit vs. corner detection vs. cubic→quadratic conversion).

4. **Minor — Enter in the shapes dialog commits the value the user has *not* just typed, and the fix moved the default focus onto that path.** `Dialog` focuses the first focusable control on open (`components/Dialog.tsx:62-70`), which in `ShapeDialog` is the X input — the old hand-rolled dialog put `autoFocus` on the Create button, and the diff dropped it (`ShapeDialog.tsx:84`). `NumberField`'s Enter handler calls `preventDefault()` but not `stopPropagation()` (`components/NumberField.tsx:83-88`), so the event reaches `Dialog`'s `onKeyDown`, which sees an `INPUT` target and calls `onConfirm` → `create()` — reading `x/y/width/height` from the current render's closure, before React has applied the `setWidth` that `NumberField` just fired. I verified this with a temporary Vitest file (since removed): opening at (40,60), typing `250` into W and pressing Enter produces `[[40,60],[140,60],[140,160],[40,160]]` — a 100×100 rectangle, the typed width discarded. The stale-closure defect predates the diff (the old div `onKeyDown` had it too); what is new is that it is now the default keyboard path, and §9 makes "Enter creates" the contract. A ref mirror of the four values, or reading them in `create()` from a `useRef`, fixes it.

5. **Minor — the fit is synchronous on pointer-up and is not cheap.** Measured with a temporary Vitest file on realistic strokes (smooth S-curve, jitter under the tolerance): 182 samples → 128 ms cubic / 102 ms quadratic; 601 samples → 108 / 185 ms; 2401 samples → 317 / 334 ms. `distanceToCubic` (`curveFit.ts:223-251`) evaluates the cubic ~36 times per sample per attempt, and every reparameterisation pass and every recursion level re-measures the whole run. §13's 60 fps contract is about the gesture, not the commit, so this does not break it, but a several-hundred-millisecond freeze at the end of a stroke is real and the report does not mention it. Memoising `derivative(bez)` out of `newtonStep` and reusing the sampled distances would take most of it.

6. **Observation (not a regression) — the 1-unit tolerance is not zoom-aware, so a stroke drawn zoomed out degenerates to one node per sample.** Same temporary probe: at a 0.25 px/unit zoom the 2-CSS-px sampling step is 8 font units and the pointer noise exceeds the tolerance, so 76 samples fit to 76 stored points; at 0.6 px/unit, 182 samples → 86 points; at 2 px/unit, 601 samples → 28 points. The corner detector itself is well behaved — zero false corners on all four realistic strokes, so the 60° threshold is not the problem. This is the ruling's fixed tolerance meeting a zoom-dependent sampling step, and it is the practical face of the implementer's own concern 2 (`Prefs` has nowhere to put a tolerance). Scaling `PENCIL_FIT_ERROR` by `2 / viewport.scale` would track it.

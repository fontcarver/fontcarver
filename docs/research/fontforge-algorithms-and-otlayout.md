# PART 1 — OpenType Layout & Features Model

## 1.1 Core data model (`fontforge/splinefont.h`)

FontForge's layout model is a **three-level tree** that mirrors OpenType's `LookupList` but inverts the feature/script/lang relationship: features hang off *lookups*, not the other way round.

**`OTLookup`** — `fontforge/splinefont.h:398-425`. Fields: `lookup_type` (an `enum otlookup_type`, `splinefont.h:275-308`, where `type & 0xff` is the OT lookup type and `type >> 8` is 0=GSUB / 1=GPOS), `lookup_flags` (uint32), `lookup_name`, `FeatureScriptLangList *features`, `struct lookup_subtable *subtables`, plus compile-time scratch (`lookup_index`, `lookup_offset`, `lookup_length`, `needs_extension`, `subcnt`, `in_gpos`, `in_jstf`, `only_jstf`, `temporary_kern`).

Notably the enum reserves values **outside** OpenType: `morx_indic=0x0fd`, `morx_context=0x0fe`, `morx_insert=0x0ff`, `kern_statemachine=0x1ff` — Apple AAT state machines are modelled as pseudo-lookups in the same list. Extension lookups (GSUB 7 / GPOS 9) are *not* a lookup type: they are synthesized at compile time (`needs_extension`).

**`lookup_subtable`** — `splinefont.h:366-395`. A subtable is a discriminated union by convention, not by tag: exactly one of `kc` (KernClass), `fpst` (contextual), `sm` (Apple state machine) is non-NULL, or the subtable is "per-glyph" (`per_glyph_pst_or_kern`) or "anchor" (`anchor_classes`). The comment at `splinefont.h:381-388` states the placement rule: kern classes / FPSTs / state machines get a subtable to themselves; anchor classes may share; glyph PSTs may share. It also carries autokern/autowidth UI parameters (`separation`, `minkern`, `kerning_by_touch`, `onlyCloser`, `dontautokern`) and the compiled offsets (`subtable_offset`, `extra_subtables[]` — a `-1`-terminated list used when a pair-pos subtable had to be split for the 64 k limit).

**Feature/script/lang** — `FeatureScriptLangList` (`splinefont.h:352-357`) is a linked list of `{featuretag, scripts, ismac}`; `scriptlanglist` (`splinefont.h:334-340`) is `{script, langs[4], morelangs[], lang_cnt}`. `DEFAULT_SCRIPT` is `'DFLT'` and `DEFAULT_LANG` is `'dflt'` (`splinefont.h:268-273`), plus a fake `REQUIRED_FEATURE = ' RQD'` tag used to represent a script's ReqFeatureIndex.

The known-feature table `friendlies[]` (`fontforge/lookups.c:~150-295`) maps each tag to a friendly name **and a bitmask of legal lookup types** (`enum otlookup_typemasks`, `splinefont.h:310-331`). E.g. `lookups.c:285` `vert → gsub_single_mask`, `lookups.c:289` `vkrn → gpos_pair|gpos_context|gpos_contextchain|kern_statemachine`. This drives the UI's "which lookup types may carry this feature" validation.

## 1.2 Mapping of GSUB/GPOS lookup types onto FF data

FontForge does **not** store per-lookup rule arrays. Rules live on the glyphs and are back-linked to a subtable pointer:

| OT type | FF storage | Definition |
|---|---|---|
| GSUB 1 single | `PST` with `type=pst_substitution`, `u.subs.variant` on the source glyph | `splinefont.h:504-518` |
| GSUB 2 multiple | `PST` `pst_multiple`, `u.mult.components` (space-separated names) | same |
| GSUB 3 alternate | `PST` `pst_alternate`, `u.alt.components` | same |
| GSUB 4 ligature | `PST` `pst_ligature` stored **on the ligature glyph**, `u.lig.components` | same; see `LigatureSearch` `lookups.c:3099` |
| GSUB 5/6, GPOS 7/8 | `FPST` (`splinefont.h:554-566`) | see §1.4 |
| GSUB 8 reverse chain | `FPST` with `format = pst_reversecoverage`, rule union `struct fpr` | `splinefont.h:547-552` |
| GPOS 1 single | `PST` `pst_position`, `u.pos` = `struct vr` (xoff,yoff,h_adv,v_adv + `ValDevTab*`) | `splinefont.h:504-518` |
| GPOS 2 pair | either `PST` `pst_pair` (`u.pair.paired` name + `vr[2]`), or `KernPair` on `sc->kerns`/`sc->vkerns`, or a `KernClass` on the subtable | `splinefont.h:468-502` |
| GPOS 3 cursive | `AnchorClass` with `type=act_curs`; `AnchorPoint`s of type `at_centry`/`at_cexit` | `splinefont.h:444-466` |
| GPOS 4 mark-to-base | `AnchorClass` `act_mark`; `at_mark` on marks, `at_basechar` on bases | same |
| GPOS 5 mark-to-lig | `AnchorClass` `act_mklg`; `at_baselig` + `lig_index` | same |
| GPOS 6 mark-to-mark | `AnchorClass` `act_mkmk`; `at_basemark` | same |
| GSUB 7 / GPOS 9 extension | synthesized only at output time | `tottfgpos.c:3171` |

`KernClass` (`splinefont.h:486-502`) is a dense `first_cnt × second_cnt` `int16_t offsets[]` array plus a parallel `DeviceTable adjusts[]`. Classes are stored as **space-separated glyph-name strings** (`firsts[]`, `seconds[]`), with class 0 meaning "everything else". The UFO round-tripping additions (`firsts_names`, `firsts_flags`, the `FF_KERNCLASS_FLAG_*` bits at `splinefont.h:477-484`) exist purely to preserve `groups.plist`/`kerning.plist` naming and the "virtual single-glyph class" hack.

Ligature caret positions are stored as a `PST` of type `pst_lcaret` (`u.lcaret.carets[]`) — i.e. GDEF lig-caret data rides in the same per-glyph list as substitutions.

## 1.3 Lookup ordering and feature-script-lang manipulation

Lookups are a **flat singly-linked list per table**: `sf->gsub_lookups`, `sf->gpos_lookups`. Execution order = list order. When a lookup is created programmatically, `SortInsertLookup` (`lookups.c:2596`) inserts it by a hard-coded feature-priority table `_FeatureOrderId` (`lookups.c:2468-2578`): GSUB `ccmp = -2`, `locl = -1`, `isol/jalt/fina/fin2/fin3/medi/med2/init = 0..7`, `rtla = 100`, `smcp/c2sc = 200`, `rlig=300, calt=301, liga=302, dlig/hlig=303, cswh=304, mset=305, frac=306`, the Indic block `nukt/pref=301 … haln=320`, unknown `= 1000`, and `vert/vrt2 = 1010` ("documented to come last"). GPOS: `curs=0, dist=100, blwm=201, abvm=202, kern=300, mark=400, mkmk=500`.

Note the loop in `SortInsertLookup` at `lookups.c:2601-2604` recomputes `FeatureOrderId(newotl)` in the condition instead of comparing against `otl` — that comparison is always false, so the function effectively prepends. This is a latent bug worth *not* reproducing.

Query helpers build the script/lang/feature axes on demand by walking every lookup: `SFScriptsInLookups` (`lookups.c:398`), `SFLangsInScript` (`lookups.c:475`), `SFFeaturesInScriptLang` (`lookups.c:538`), `SFLookupsInScriptLangFeature` (`lookups.c:625`). Ordering/merging helpers: `LangOrder`/`SLOrder`/`FLOrder` (`lookups.c:1819-1896`), `SLMerge`/`FLMerge` (`lookups.c:1962-1999`), and `SFSubTablesMerge` (`lookups.c:2001`) which merges two subtables' contents if type-compatible. Cross-font copying goes through `OTLookupCopyInto` / `OTLookupsCopyInto` (`lookups.c:2739`, `2755`) with a `sfmergecontext` that maps old→new lookups, subtables, anchor classes and prefixes names on collision (`NeedsPrefix`, `lookups.c:2701`).

`aalt` is special-cased: `AddNewAALTFeatures` (`lookups.c:4512`) removes old generated lookups (`AALTRemoveOld`, `4270`), collects per-script "single+alternate" lookup sets into `struct sllk` (`AddOTLToSllks`, `4411`), and synthesizes one `gsub_alternate` lookup per script whose components are the union of all single/alternate targets (`ComponentsFromPSTs`, `4344`; `NewAALTLookup`, `4434`).

## 1.4 Contextual chaining (FPST)

`FPST` (`splinefont.h:554-566`) has `type` ∈ {`pst_contextpos`, `pst_contextsub`, `pst_chainpos`, `pst_chainsub`, `pst_reversesub`} and `format` ∈ `pst_glyphs | pst_class | pst_coverage | pst_reversecoverage` (`splinefont.h:520-521`). Class lists `nclass/bclass/fclass` (+ `*_names` for FEA round-trip). Each `fpst_rule` (`splinefont.h:541-552`) is a union over the four formats:

- `struct fpg glyph` — three space-separated name strings `names`/`back`/`fore`.
- `struct fpc fpc_class` — `uint16_t` class-index arrays `nclasses/bclasses/fclasses`.
- `struct fpv coverage` — arrays of coverage strings `ncovers/bcovers/fcovers`.
- `struct fpr rcoverage` — reverse: `always1` (must be 1), coverage arrays, plus a `replacements` string.

**Backtrack is stored in reverse textual order** (comment at `splinefont.h:542-544`) matching the OT wire format; the UI reverses it again (`reverseGlyphNames`, `lookups.c:4749`). Rules carry `struct seqlookup {seq, lookup}` arrays for nested lookup invocation (`splinefont.h:531-534`).

Human-readable serialization is `FPSTRule_To_Str` / `FPSTRule_From_Str` (`lookups.c:4773`, `4890`) — the format used by the UI and the SFD.

Output: `dumpg___ContextChain` dispatches on format (`tottfgpos.c:2642-2657`) to `…Glyphs` (fmt 1), `…Class` (fmt 2), `…Coverage` (fmt 3). Reverse chaining shares the coverage writer, which emits **format 1** and asserts `rule_cnt==1` and `always1==1` (`tottfgpos.c:2540-2548`). So FontForge only supports single-rule reverse-chain subtables.

## 1.5 Lookup flags

`enum pst_flags` (`splinefont.h:361-364`): `pst_r2l=1`, `pst_ignorebaseglyphs=2`, `pst_ignoreligatures=4`, `pst_ignorecombiningmarks=8`, `pst_usemarkfilteringset=0x10`, `pst_markclass=0xff00`. The mark **filtering set index** lives in the high 16 bits (`#define pst_markset 0xffff0000`), so `lookup_flags` is a 32-bit value that is *not* the wire format — the wire `lookupFlag` is the low 16 bits and `markFilteringSet` is a separate uint16.

Mark attachment classes and mark filtering sets are font-global name→glyph-list arrays: `sf->mark_classes[]`/`mark_class_names[]`/`mark_class_cnt` and `sf->mark_sets[]`/`mark_set_names[]`/`mark_set_cnt`. They compile into GDEF (`tottfgpos.c:3826-3878`).

The runtime interpretation of flags is `skipglyphs` (`lookups.c:3140-3168`), `bskipglyphs` (`3200`), and `bskipmarkglyphs` (`3170`) — the last unconditionally skips marks backwards regardless of flags, used for mark-to-base/mark-to-lig (see comment at `lookups.c:3641-3646`).

## 1.6 The apply engine (metrics-view preview)

Entry point: `ApplyTickedFeatures(sf, flist, script, lang, gpos_only, pixelsize, glyphs)` — `lookups.c:3861-3907`. It builds a `struct lookup_data` (`lookups.c:2782-2794`) holding an array of `struct opentype_str` (one per glyph, with `sc`, `orig_index`, `vr`, `lig_pos`, `context_pos`, `kc`/`kc_index`, `kp`), a pixel size and a scale factor `pixelsize / (ascent+descent)`.

Algorithm:
1. For `isgpos` in {0,1}: check the script has the requested language, else fall back to `dflt` (`lookups.c:3884-3891`).
2. Walk the lookup list in order; `FSLLMatches` (`lookups.c:3828`) tests whether the lookup carries any of the requested feature tags for `(script, lang)`; if so `ApplyLookup(tag, otl, data)`.
3. `ApplyLookup` (`lookups.c:3810`) dispatches AAT state machines to `ApplyAppleStateMachine` (`lookups.c:2990`), otherwise sweeps positions left-to-right calling `ApplyLookupAtPos`, forcing `pos+1` progress if the handler returns ≤ pos.
4. `ApplyLookupAtPos` (`lookups.c:3737`) first applies conditional tag semantics — `ConditionalTagOk` (`lookups.c:3712`) synthesizes `init/isol/fina/medi` behaviour by comparing `SCScriptFromUnicode` of neighbours, so those features work even without a proper Arabic shaper. Then it tries each subtable in order; **first subtable that returns non-zero wins**. `gpos_pair` gets *two* passes (`pcnt=2`): the second pass allows matching the class-0 "Everything Else" class (`allow_class0`).

Per-type handlers: `ApplySingleSubsAtPos` (3364), `ApplyMultSubsAtPos` (3388), `ApplyAltSubsAtPos` (3437 — takes the first alternate), `ApplyLigatureSubsAtPos` (3462, uses the precomputed `LigatureSearch` table and tags absorbed marks with `lig_pos`), `ApplyContextual` (3512), `ApplySinglePosAtPos` (3542), `ApplyPairPosAtPos` (3562), `ApplyAnchorPosAtPos` (3634).

`ContextualMatch` (`lookups.c:3230-3362`) is the chaining matcher: it resets `context_pos`, matches backtrack (backwards, respecting skips), then input (recording `context_pos = cpos++` per matched slot), then lookahead. Class 0 matching is done by *failing to match every other class* (`lookups.c:3288-3298`) — O(nclasses) per glyph, since coverage is stored as strings. It explicitly **refuses reverse chaining**: `return 0` with the comment "Not ready to deal with reverse chainging" (`lookups.c:3308`). Meanwhile `ApplyLookupAtPos` routes `gsub_reversecchain` to `ApplySingleSubsAtPos` (`lookups.c:3763-3765`), i.e. it applies the substitution unconditionally, ignoring the context.

Positioning is accumulated into `str[i].vr` in **pixels** (`rint(value * scale)`), with `FigureDeviceTable` adding device-table deltas — and that function has an off-by-design bug: it indexes `corrections[pixelsize - dt->last_pixel_size]` instead of `- first_pixel_size` (`lookups.c:3533-3540`).

Anchor positioning (`lookups.c:3634-3710`) is "walk backwards from the mark": find the mark/entry anchor on the current glyph, back up (mark-skipping for mark2base/mark2lig, flag-skipping otherwise), find the matching base/exit anchor, and set `vr.xoff/yoff` **absolutely** (`=`, not `+=`) relative to the base's own offsets, subtracting the base advance in the LTR case. The comment admits "This probably doesn't work for vertical text" (`lookups.c:3698`).

Notably: **no lookup nesting depth limit, no cycle detection**, and glyph-class membership is tested by substring search over space-separated name strings (`GlyphNameInClass`, `lookups.c:2799`). For a Rust port this should be replaced by interned glyph IDs + bitsets/`Coverage` maps.

### Writer

`FeatDumpFontLookups` (`featurefile.c:2004-2022`) emits, in order: mark-class declarations (`gdef_markclasscheck`), `languagesystem` header (`dump_header_languagesystem`, `1736`), GSUB then GPOS (`dump_gsubgpos`, `1819`), `table GDEF` (`dump_gdef`, `1560`), `table BASE` (`dump_base`, `1710`). Lookup names are made unique in ≤31 chars by `preparenames` (`featurefile.c:1923-1994`).

`dump_lookup` (`1348`) writes `lookupflag` symbolically when possible and falls back to a numeric flag when bits 5–7 are set (`1372-1374`). ## 1.8 `tottfgpos.c` — compilation to GPOS/GSUB/GDEF

**Pair positioning, format 1** — `dumpGPOSpairpos` (`tottfgpos.c:1243-1508`).
1. Collect first glyphs in GID order (`SFOrderedGlyphsWithPSTinSubtable`, `820`); for each, collect its second glyphs from `possub` (`pst_pair`) and from `kerns`/`vkerns`, sort by GID (`cmp_gid`, `1238`).
2. Detect glyphs whose entire second-glyph list is *identical* to an earlier glyph's, recording `samewas` (`1305-1337`) — a primitive value-record sharing scheme that reuses the offset instead of re-emitting the `PairSet`.
3. Compute `ValueFormat1`/`ValueFormat2` masks by OR-ing over all pairs (`1342-1390`); if both end up zero, force `vf1=1`.
4. **Subtable splitting**: greedily accumulate glyphs while `len ≤ 65535`, where `len` starts at 10 (subtable header) and each glyph adds 2 + `(bit_cnt*2+2)*tot + devtablen + 2` (`1400-1420`). Overflow points push a new offset into `sub->extra_subtables[]`. Two diagnostics: a single glyph whose data exceeds 64 k (`1414`) and the general "had to be split into several subtables" (`1418`).
5. Emit; verify at the end that the subtable really is < 64 k, else `IError` "the kerning output is wrong" (`1497`).

**Pair positioning, format 2** — `dumpgposkernclass` (`tottfgpos.c:1629-1704`). Straightforward: ValueFormat is `0x0004` (XAdvance) or `0x0008` (YAdvance, decided by whether the `KernClass` is on `sf->vkerns`), OR'd with `0x0040`/`0x0080` if any device table exists. Class definitions come from `ClassesFromNames` (`1518`) which maps name-strings to a `uint16_t[numGlyphs]` array; `DumpClass` (`1591`) writes ClassDef format 2 ranges. **No 64 k splitting is attempted for class kerning** — a `first_cnt × second_cnt` array over ~2 bytes/cell overflows silently above ~32 k cells.

**Anchors** — `AnchorClassDecompose` (`586`) partitions an anchor class into mark/base/lig/mkmk glyph arrays; `EntryExitDecompose` (`663`) does cursive. `AnchorsAway` (`2663`) drives `dumpgposCursiveAttach` (`1731`) and `dumpgposAnchorData` (`1844`). The latter handles MarkBasePos/MarkMarkPos (fixed `BaseArray`, three passes: size, offsets, data — `1863-1898`) and MarkLigPos (`LigArray` with per-component rows indexed `k*max + lig_index`, `1900-1960`). Anchor records are written by `dumpanchor` (`1707`): format 3 if device tables, format 2 if a TrueType point index exists and the font is TTF, else format 1. Marks are re-emitted per subtable rather than shared, with an explicit comment that sharing broke subtable reordering (`2020-2021`).

**GDEF** — `gdefclass` (`tottfgpos.c:3668-3703`) derives the class when `sc->glyph_class` is unset: `.notdef → 0`; any non-cursive anchor of type `at_mark`/`at_basemark` → 3 (mark) — deliberately preferred over ligature; any `pst_ligature` → 2; unencoded + has dependents + CID font + not referenced by GSUB → 4 (component); else 1 (base). `otf_dumpgdef` (`3705`) emits ClassDef format 2 (a comment says ttx can't handle format 1, `3757`), always emits a LigCaret list even if empty (`3792-3799`), then the MarkAttachClassDef and — if `mark_set_cnt>0` — bumps the version to `0x00010002` and writes the MarkGlyphSets table.

**Lookup ordering & extension subtables** — `G___figureLookups` (`2875`) assigns `lookup_index`, skipping unused / Apple-only (`OnlyMac`, `2737`) / JSTF-only / temporary-kern lookups. If the combined lookup data exceeds 64 k it re-orders lookups **smallest-first** (`lookup_size_cmp`, `2719`) to minimise extension use, rewriting subtable offsets by the delta. `g___FigureExtensionSubTables` (`3171`) then iterates to a fixed point: mark any lookup whose subtable offset would exceed 65535 as `needs_extension`, add `8 * subcnt` bytes, repeat; then emit 6-byte-per-subtable ExtensionPos/Subst records (format 1, `lookup_type & 0xff`, 32-bit offset).

**`size`** — `dumpg___info` (`3275`) reserves the FeatureParams pointer while writing the FeatureList and backfills `designSize / subfamilyID / nameID / rangeStart / rangeEnd` from `sf->design_size`, `fontstyle_id`, `design_range_bottom/top` (`3376-3391`); the menu name is allocated a fresh `name` table string ID (`at->fontstyle_name_strid`). `ss01–ss20` and `cv01–cv99` FeatureParams are written by `getfeatnamefromginfo` (`3259`) / the block at `3392-3430`.

**MATH** — `otf_dump_math` (`4307`); `MathBits` (`3880`) decides which subtables are needed. ## 1.9 Apple AAT (`tottfaat.c`, `asmfpst.c`)

`aat_dumpmorx` (`tottfaat.c:1899`) builds a `morx` chain from the same GSUB data: substitutions (`aat_dumpmorx_substitutions`, `648`), ligatures (`aat_dumpmorx_ligatures`, `953` — with the ligature state machine built by `morx_dumpLigaFeature`, `725`), explicit `ASM`s (`aat_dumpmorx_asm`, `1318`), OpenType contextual lookups converted on the fly (`aat_dumpmorx_cvtopentype`, `1340`), and Arabic form features synthesized into a cursive-connection state machine (`aat_dumpmorx_cvtopentypeforms`, `1455`; `IsOtfArabicFormFeature`, `1354`; `HasCursiveConnectionSM`, `1368`). `Macable` (`1423`) is the gate: a lookup is Mac-able if its feature tag maps to a `(featureType, featureSetting)` pair (`OTTagToMacFeature`, `2448`) and it has a default script. The `feat` table is generated from the collected feature list (`aat_dumpfeat`, `1586`) including synthesized "no-op" settings for exclusive feature types (`AddExclusiveNoops`, `1525`).

Other AAT tables from the same model: `lcar` from `pst_lcaret` (`aat_dumplcar`, `441`), `opbd` from left/right-bound PSTs (`aat_dumpopbd`, `2001`; `haslrbounds`, `1981`), `prop` from `gdefclass` + Unicode bidi/mirroring data (`props_array`, `2087`; `aat_dumpprop`, `2186`), `bsln` from `struct Base` (`BslnFromTag`, `2243`; `PerGlyphDefBaseline`, `2260`; `FigureBaseOffsets`, `2321`; `aat_dumpbsln`, `2357`), and `acnt` (stub, `aat_dumpacnt`, `52`).

`asmfpst.c` is the FPST↔state-machine bridge. `FPSTGlyphToClass` (`71`) normalises a glyph-format FPST into class format. `FPST2Tree` (`344`) builds a trie of the rules (`_FPST2Tree`, `263`; `TreeFollowBranches`, `219`; `TreeLabelState`, `163`), then `ASMFromClassFPST` (`953`) walks the trie emitting `asm_state` transitions with `SMSetState` (`883`) and `AnyActiveSubstrings` (`912`) providing failure-transition fallback (an Aho–Corasick-flavoured construction). Coverage-format FPSTs take a different path, `ASMFromCoverageFPST` (`783`), which synthesizes classes from the cross-product of coverage sets (`morx_cg_FigureClasses`, `673`). `FPSTisMacable` (`397`) is the feasibility test: contextual/chain-sub only, a Mac-mappable feature tag, and for coverage format at most ~10 total positions and at most 2 nested lookups with the second on the final glyph.

# PART 2 — Geometry / Algorithm Modules

## `splineoverlap.c` (3996 lines)

- **Approach.** Documented in the 55-line header comment at `splineoverlap.c:49-84`. (1) Decompose every spline into **monotonic sub-splines** (`SplineToMonotonic`, `206`; `SSsToMContours`, `394`) that are monotone in both x and y, kept as `{spline, tstart, tend}` views rather than real splines to avoid re-rounding. (2) Pairwise intersect (`FindMonotonicIntersection`, `1655`) with special handling for coincident splines (`CoincidentIntersect`, `2005`), producing `Intersection` nodes with `MList` spoke lists; a lot of the file is intersection *repair* — `MoveIntersection` (552), `MergeIntersections` (626), `ImproveInter` (1239), `SplitMonotonicAtT/AtFlex/AtFake` (997/1083/1228), `AddCloseIntersection` (1593), `TryHarderWhenClose` (2517). (3) Winding: shoot a scanline along the minor axis (`FindOrderedEndpoints`, `2367`; `MonotonicFindAt`, `2425`; `FigureNeeds`, `2675`) and mark each monotonic "needed" per `IsNeeded` (`2662`) — `remove`: winding==0 on either side; `intersect`: |winding|≥2 on exactly one side; `exclude`: uses a separate `ew` (exclude-winding) counter. (4) Re-trace contours from intersection to intersection (`JoinAContour`, `3149`; `MonoFollowForward/Backward`, `3064`/`3106`; `JoinAllNeeded`, `3282`).
- **In/Out.** `SplineSetRemoveOverlap(sc, base, ot)` (`3955`) — `SplineSet*` in, `SplineSet*` out; `over_findinter`/`over_fisel` instead annotate the input (`FixupIntersectedSplines`, `3435`). Pre-passes: `SSRemoveTiny` (3465), `SSRemoveStupidControlPoints`, `SplineSetsRemoveAnnoyingExtrema(base, .3)`. Also exposed: `SSRemoveBacktracks` (3765), `SSRemoveReversals` (3863, currently disabled — see the comment at `3969-3971`).
- **Weaknesses.** Extremely fragile numerically; the file is riddled with `SOError` internal-error reports and a `FF_OVERLAP_VERBOSE` diff-based debugging protocol (`88-92`). Open contours are dropped from the boolean and merged back verbatim (`SSToMContour`, `346`). No support for even-odd fill or for stroke-and-fill. Comment at `3969` documents an unfixed regression around reversals.
- **Rust option.** `kurbo` has no boolean ops. Real options: **`skia-safe` pathops** (Skia's `SkPathOps` — production-grade, handles conics/quads/cubics, both fill rules), or `path-bool` / `vello`'s upcoming work, or `i_overlay` (fast but polygon/flattened). `lyon` has `lyon_path::path_buffer` + `lyon_tessellation` fill but no boolean path output.
- **Recommendation. Use crate (skia-safe pathops) for the common cases, with a fallback.** Porting 4000 lines of numerically-tuned C is the single highest-risk item in this project and the payoff is low: Skia's pathops has orders of magnitude more test exposure. Keep FontForge's *pre-passes* (remove-tiny, stupid-control-points, remove-backtracks) as your own Rust code because they encode font-specific cleanup Skia doesn't do. If you need exact cubic-preserving output (Skia returns cubics but re-fits at intersections), consider a hybrid: Skia for topology, your own re-fit.

## `splinestroke.c` (2694 lines)

- **Approach.** This is Skef Iterum's rewrite (post-2019), not the old George Williams code. The nib is a **convex closed contour** (`NibIsValid` → `Shape_Convex`), modelled as `NibCorner[]` — for each corner the incoming and outgoing unit tangents (`splinestroke.c:88-93`). Offsetting works by, for each tangent direction along the source spline, finding the nib point whose tangent matches (`NibOffset`, `120-131`: `nci[2]`, `off[2]`, `nt`, `at_line`, `curve`, `reversed`), then tracing the offset curve and fitting. Joins are inserted by walking nib corners between the incoming and outgoing tangent. Types: `nib_ellip`, `nib_rect`, `nib_convex` (`80`). `StrokeInfo` (`splinefont.h:139-157`) carries `si_round | si_calligraphic | si_nib | si_centerline`, `join` (`lj_nib`, `lj_arcs`, plus PS miter/round/bevel, `splinefont.h:104-112`), `cap` (`lc_butt/round/square/nib/bevel`), `joinlimit` + `jlrelative`, `extendcap` + `ecrelative`, `removeinternal`/`removeexternal`, `rmov` (`srmov_layer/contour/none`), `al` (`sal_auto/svg2/ratio`), `accuracy_target`.
- **In/Out.** `SplineSetStroke(ss, si, order2)` (`2533-2650`). Quadratic input is converted to cubic (`SSPSApprox`) first (`2495-2498`); CCW contours are reversed before offsetting and restored after (`2491`, `2512`). Post-passes: layer-wide remove-overlap, `SplineCharAddExtrema`, `SplineCharSimplify` with a fixed `simplifyinfo` (`2540-2542`, err = `accuracy_target`). Also public: `SSAppendArc` (`1019`), `StrokeGetConvex` (`226`, cached regular-polygon nibs), `UnitShape` (`2400`).
- **Weaknesses.** `si_centerline` is unimplemented (`IError("centerline not handled")`, `2545`). Only convex nibs. Elliptical nibs are emulated by transforming a unit circle, so the offset for an ellipse is exact only because the tangent-matching is done in nib space. Remove-inner/outer is implemented via winding tricks rather than a proper boolean.
- **Rust option.** `kurbo::stroke` (Levien's 2022 stroke expansion) is excellent for *round* nibs with proper Euler-spiral-quality offsetting and correct caps/joins including miter limits; it does not do arbitrary polygonal/calligraphic nibs. `lyon_tessellation`'s stroke tessellator produces triangles, not paths — useless here. `zeno`/`raqote` similar.
- **Recommendation. Hybrid.** Use `kurbo::stroke` for circular nibs (the 90 % case: "Expand Stroke" with a round pen) — it will be faster, better-tested and produces fewer points. **Port** the nib-corner machinery for calligraphic/polygonal/arbitrary-convex nibs; that capability has no Rust equivalent and is a genuine FontForge differentiator. The `NibOffset` abstraction is clean enough to port directly.

## `splinefit.c` + `splineutil2.c` (1412 + 4432 lines)

- **Approach.** `ApproximateSplineFromPoints` (`splinefit.c:326`) solves for a cubic through fixed endpoints minimising least-squares error to sampled `FitPoint`s; `_ApproximateSplineFromPoints` (`96`) is the linear-algebra core; `IsLinearApprox` (`40`) short-circuits to a line. `ApproximateSplineFromPointsSlopes` (`643`) is the slope-preserving variant: for order-2 it has a unique answer (intersect the two tangent lines, `684-703`); for cubics it does a **local search** over control-point lengths (`TRY_CNT` candidates, `bestdiff[]`/`besti[]`/`bestj[]`) scored by `SigmaDeltas` (`432`) with `ApproxBounds` (`509`) and `ClosestSplineSolve` (`404`) providing the error metric. Simplification: `SplinePointListSimplify` (`splineutil2.c:1940`) runs cleanup passes (`RemoveZeroLengthSplines`, `SSRemoveBacktracks`, `SPLStartToExtremum`, `SPLNearlyHvLines`, `SPLForceLines`), then tries removing *whole runs between extrema* first (`1967-2000`), then point-by-point (`SplinesRemoveMidMaybe`, `1497`). Flags are `enum simpify_flags` (`splinefont.h:166-170`): `sf_ignoreslopes`, `sf_ignoreextremum`, `sf_smoothcurves`, `sf_choosehv`, `sf_forcelines`, `sf_nearlyhvlines`, `sf_mergelines`, `sf_setstart2extremum`, `sf_rmsingletonpoints`; `struct simplifyinfo` adds `err`, `tan_bounds`, `linefixup`, `linelenmax`.
- Extrema: `SplineAddExtrema` (`splineutil2.c:2624`) with `lenbound`/`offsetbound`/`emsize` thresholds and `ForceEndPointExtrema` (`2508`) which nudges near-extremal endpoints; `enum ae_type` selects all/selected. Inflections (`SplineAddInflections`, `2884`), balance (`SplineBalance`, `2929`) and harmonize (`SplinePointHarmonize`, `3001`) are newer additions.
- Direction: `SplineSetsCorrect` (`splineutil2.c:4009`) rasterizes with the scanline `EdgeList` machinery, walks the active-edge list at "interesting" scanlines and flips contours whose winding contradicts the nesting rule (outermost clockwise, alternating inward). `SplineSetsDetectDir` (`4091`) is the read-only variant. `SplineSetsRound2Int` is in `splinechar.c:856` (spiro-aware).
- Order conversion: `SSttfApprox` (`splineorder2.c:858`) → `ttfApprox` (`721`) → `_ttfapprox`/`__ttfApprox` (`387`) recursively splits a cubic at "magic points" (inflections and where the quadratic error exceeds tolerance) and emits quadratics with the standard `(c + 2d)/2` control point (`704-715`), snapping to integers when the endpoints are integral or half-integral (TrueType implied-point condition, `728-733`). `SSPSApprox` (`960`) goes the other way with the classic 2/3 rule plus `ImproveB3CPForQuadratic` (`~900-957`) which tries 9 perturbations of the two control points and picks the best. `SplineSetsConvertOrder` (`1022`) is the dispatcher.
- **Weaknesses.** The cubic fitter is a hand-rolled hill climb, not a proper Schneider/Levien fit; results are order-dependent and occasionally produce loops. Simplify's flag matrix is under-documented and interacts badly with hints. The order-2 approximation is not error-bounded in a provable way.
- **Rust option.** `kurbo` covers this territory well: `kurbo::fit_to_bezpath` / `fit_to_bezpath_opt` (Levien's optimal cubic fitting, 2022), `CubicBez::to_quads` (error-bounded cubic→quadratic!), `ParamCurveExtrema` for extrema, `ParamCurveArclen`, `simplify::simplify_bezpath` with tolerance. `kurbo`'s `to_quads` is strictly better-founded than `ttfApprox`.
- **Recommendation. Use crate (kurbo) for the primitives; port the policy.** Use `kurbo` for fitting, extrema, arclen and cubic↔quadratic. **Port** the *font-specific policy layer*: the simplify flag semantics (`sf_forcelines`, `sf_nearlyhvlines`, `sf_choosehv`, `sf_setstart2extremum`), `SPLForceLines`, the "remove everything between extrema first" strategy, contour canonicalisation (`CanonicalContours`, `splineutil2.c:2192`; `SPLsStartToLeftmost`, `2150`), and `SplineSetsCorrect`. Correct-direction specifically: consider replacing the scanline algorithm with a simple signed-area + point-in-polygon nesting test, which is what everyone else does and is far more robust.

## `stemdb.c` + `autohint.c` (6088 + 3452 lines)

- **Approach.** `stemdb.c` builds a `struct glyphdata` (`stemdb.h:38-70`): every on-curve and control point becomes a `pointdata`; lines are grown from points (`BuildLine`), then stems are grown by pairing points on opposite edges (`BuildStem`, `GlyphDataBuild` at `5871-5990`), with diagonal stems handled when `detect_diagonal_stems`. Stems are grouped into `stembundle`s (h/v/inclined) and get `segment` activity ranges. `GlyphDataInit` (`5745`) sets up geometry, `use_existing` lets the autoinstructor reuse manual hints. Blue zones come from `QuickBlues` (`autohint.c:436`) or `FindBlues` (`96`, which computes BlueValues/OtherBlues from actual glyph extrema with `AddBlue`/`MergeZones`). `FigureStems` (`autohint.c:3085`) → `FindHStems`/`FindVStems` (`3190`/`3194`) computes StdHW/StdVW and StemSnapH/V histograms.
- `autohint.c` converts `stemdata` to `StemInfo`/`DStemInfo` (`GDFindStems`, `2836`; `GDFindDStems`, `2876`), removes flex candidates (`StemRemoveFlexCandidates`, `1162`), then computes hint *instances* (the y-ranges where each hint is active) via `SCGuessHintInstancesList` (`1571`). **Hint substitution** is `SCFigureHintMasks` (`2776`) → `SplFigureHintMasks` (`2717`) → `FigureHintMask` (`2291`)/`TestHintMask` (`2351`): walk the contour, and at each point choose the minimal conflict-free hint set (`ConflictsWithMask`, `2278`), emitting a `HintMask` on the point where the set changes; `ResolveSplitHints` (`2665`) handles MM consistency. Counter masks: `SCFigureCounterMasks` (`2163`), `SCFigureVerticalCounterMasks` (`2130`), `FigureCounters` (`2106`). Flex detection is `_SplineCharIsFlexible` (`3222`) using `IsFlexSmooth` (`3198`) and a `blueshift` bound; `SCUnflex` (`3391`) undoes it.
- **In/Out.** `SplineCharAutoHint(sc, layer, bd)` (`autohint.c:2987`) mutates `sc->hstem`/`vstem`/`dstem`/`countermasks` and per-point `hintmask`s. `SplineFontAutoHint` (`3021`). There is a hard-coded oddity at `autohint.c:2963-2969`: horizontal stem widths within 0.005 of 20 or 21 are snapped exactly.
- **Weaknesses.** 6000 lines with very high coupling; `struct glyphdata` is a god-object. Quality is mediocre by modern standards — it predates and does not use the ideas in Adobe's `psautohint`. Diagonal-stem detection is off by default in some paths.
- **Rust option.** No general Rust crate. `fontc`/`fontations` do not autohint. `psautohint` is C/Python; `ttfautohint` is C and TrueType-only. There is no `kurbo`-adjacent hinting crate.
- **Recommendation. Port selectively, or shell out.** The blue-zone/StdHW/StemSnap computation (`FindBlues`, `FigureStems`) is small, valuable and easy to port. The stem detector itself is the expensive part; strongly consider **linking Adobe's `psautohint` algorithm** (BSD-licensed, well-specified) rather than porting `stemdb.c`. If you must port, port `stemdb.c` first as a standalone "stem database" crate with a clean API and reuse it for both PS hinting and TT instructing, as FontForge does.

- **Recommendation. Do not port. Shell out to `ttfautohint`** (or link `libttfautohint`) and keep the FontForge instructor only as a legacy import path. If you need in-process, wrap `ttfautohint` via FFI. This module has the worst effort-to-value ratio in the list.

## `autowidth.c` (1528) / `autowidth2.c` (1057)

- **Approach (v1, `autowidth.c:47-90` comment).** Detect serif height, guess cap-height/x-height/descender, mask out serif zones, then for each glyph build a ~60-entry left/right edge profile. Visual separation of a pair = a heuristic reduction over the per-band gaps. Then per-glyph sidebearing = `2*(spacing-average)/3 + average - local_average`. Autokern uses the same profiles: `kern = dspace - (rb - lb - visual)`.
- **Approach (v2, `autowidth2.c`).** Cleaner and the one actually used today. `aw2_findedges` (`313`) samples each glyph's left/right silhouette at integer y using the *monotonic* machinery from `splineoverlap.c` (`MonotonicFindY`, `299`) — so the profile is exact, not rasterized. `aw2_bbox_separation` (`46`) computes a weighted mean gap with weight `1/(sep+denom)²` where `denom = emsize/50` (`DENOM_FACTOR_OF_EMSIZE`, `44`) — near contacts dominate, which is why "T" vs "o" behaves. There is a Python hook (`PyFF_GlyphSeparationHook`, `57-60`) to override it. `aw2_figure_lsb`/`aw2_figure_rsb`/`aw2_figure_all_sidebearing` (`86`/`109`/`132`) solve for sidebearings; `ak2_figure_kern` (`210`), `ak2_figure_touch` (`216`), `ak2_figure_kernclass` (`238`), `ak2_figure_touchclass` (`260`) do kerning, including class kerning where the class value is the min/aggregate over members.
- **In/Out.** `AutoWidth2(fv, separation, min_side, max_side, …)` (`456`), `AutoKern2(sf, layer, left[], right[], subtable, …)` (`587`), `AutoKern2NewClass` (`715`), `AutoKern2BuildClasses` (`824`), `GuessOpticalOffset` (`536`).
- **Weaknesses.** Purely bbox/profile based — no notion of script, no roundness compensation, no optical corrections for diagonals. The v1 code is effectively dead weight.
- **Rust option.** None. (`HT Letterspacer` is Python; `kernagic` is C.)
- **Recommendation. Port `autowidth2.c` only.** It is ~1000 lines, self-contained, and the algorithm is genuinely good. Drop `autowidth.c`. Replace the `MonotonicFindY` dependency with a direct "intersect contour with horizontal line" using `kurbo::ParamCurve::solve_t_for_x`-style root finding, which removes the coupling to the overlap module. Keep the pluggable separation function as a trait — that's what the Python hook is for.

## `scstyles.c` (6956 lines)

- **Approach.** Five loosely related feature families.
  1. **Generic change / Change Weight** — `struct genericchange` (`baseviews.h:368-395`): independent scale+add for stem height/width, serif height/width, horizontal counters, LSB/RSB, plus a `fixed_maps` vertical position mapping. `ChangeGlyph` (`scstyles.c:1587`) works on the *stem database*: `PosStemPoints` (`741`) and `StemPosDependent` (`373`) move each point according to which stems own it, so stems keep their weight while counters scale independently. `FVGenericChange` (`2869`), `CVGenericChange` (`3027`).
  2. **Embolden** — `enum embolden_type {embolden_lcg, embolden_cjk, embolden_auto, embolden_custom}` (`baseviews.h:256`) with `struct lcg_zones` (`227-253`) carrying top/bottom zones and bounds, `counter_type` (`ct_squish/ct_retain/ct_auto`), a per-type `embolden_hook`, `stroke_width` and blue data. `SCEmbolden` (`4025`) strokes the outline with `SplineSetStroke` then applies the hook: `LCG_EmboldenHook` (`3744`) or `LCG_HintedEmboldenHook` (`3829`) which uses hints (`MightBeOnHint`, `3682`) to decide which side of a stem a point is on; `AdjustCounters` (`4002`). `LCG_ZoneInit` (`4112`), `PerGlyphInit` (`4230`), `FVEmbolden` (`4297`).
  3. **Condense/Extend** — `struct counterinfo` (`baseviews.h:263-282`) with `c_factor/c_add` for counters and `sb_factor/sb_add` for sidebearings, plus `ci_zones` per stem. `SCCondenseExtend` (`3390`), `FVCondenseExtend` (`3478`).

- **Recommendation. Port the generic-change + embolden + condense/extend core; skip or heavily rewrite italic.** The first three are a thin layer over the stem database and are genuinely useful. Small caps is worth porting (it's mostly bookkeeping + `genericchange`). The italic converter's serif surgery is the kind of code that should be redesigned rather than transliterated.

## `effects.c` (801 lines)

- **Approach.** `FVOutline` (`45`) = stroke the outline with `width*2` and `removeexternal=true`, append the result to the existing contours, then `SplineSetsCorrect` — i.e. outline is "original + inner offset with corrected winding". `FVInline` (`79`) does it twice, at `width*2` and `(width+inset)*2`. `FVShadow`/`SSShadow` (`777`/`703`) is a genuine 2.5-D construction: orient edges (`OrientEdges`, `158`), extrude each silhouette point along the light direction into a "line" (`SpMove`, `120`; `AddVerticalExtremaAndMove`, `219`), then clip the extruded quads against the original shape (`ClipTo3D`, `684`; `ClipBottomTo3D`, `616`; `BottomFindIntersections`, `455`; `MergeLinesToBottoms`, `577`). Wireframe is the same code with the fill removed.
- **In/Out.** All operate in place on `sc->layers[layer].splines`, with `SCPreserveLayer` for undo.
- **Weaknesses.** Outline/inline depend entirely on remove-overlap and correct-direction being right; they fail on self-intersecting glyphs. Shadow is 800 lines of ad-hoc 2.5-D clipping.
- **Rust option.** Outline/inline: trivially expressible as `kurbo::stroke` + boolean. Shadow: none.
- **Recommendation. Rewrite, don't port.** Outline/inline should be `stroke ∪ original` / `stroke_outer − stroke_inner` expressed with your boolean-op crate — 30 lines instead of 120, and correct on self-intersecting input. Shadow: port `SSShadow` if you want the feature, but it is a nice-to-have.

## `nonlineartrans.c` (928 lines)

- **Approach.** A tiny recursive-descent expression compiler: tokenizer `gettoken` (`71`) with `backup` (`180`), precedence levels `gete0`…`gete5` (`192`-`350`) and `getexpr` (`350`), producing a `struct expr` tree freed by `nlt_exprfree` (`62`). `evaluate_expr` (`392`) is the interpreter; variables are `x`, `y` plus math functions. Application: `NLTransPoint` (`512`) transforms a point, `SplineSetNLTrans` (`562`) transforms a whole contour — crucially it does **not** just move control points; it re-fits each spline by sampling and calling the fitter, because a nonlinear map does not preserve Béziers. Anchors get transformed too (`SCNLTransAnchors`, `651`). Entry points: `SFNLTrans` (`721`), `SSNLTrans` (`739`), `SCNLTrans` (`760`), `CVNLTrans` (`778`).
- **3D perspective** reuses the same machinery: `struct pov_data` (`baseviews.h:216`), `BpPoV` (`800`) computes `z = pov->z + y*sin(tilt)`, divides by `z/d`, clamps to ±32768; `SPLPoV` (`819`) rotates into view space, applies the point map through `SplineSetNLTrans` with a function pointer (`c.pov_func`), then rotates back and averages control points (`SPLAverageCps`).
- **Weaknesses.** Ad-hoc expression language with no documented grammar; error reporting is minimal. Clamping to ±32768 silently mangles extreme perspectives.
- **Rust option.** For the expression language: `evalexpr`, `meval`, `fasteval`, or `rhai`. For the geometry: nothing needed beyond your fitter.
- **Recommendation. Hybrid — use a crate for the expression evaluator, port the geometry glue.** `fasteval` or `evalexpr` gives you a better language for free (and lets you keep FontForge-compatible syntax with a small shim). The `SplineSetNLTrans` "sample + refit" pattern is the part worth keeping, and it's ~90 lines.

## `fvcomposite.c` (2967 lines)

- **Approach.** Given a glyph with a Unicode code point, decompose via NFD (`SFGetAlternate`, `1120`, with `SFAlternateFromLigature`, `1060`, and `arabicfixup`, `1033`), then place a base reference (`SCMakeBaseReference`, `1696`) and each accent (`SCCenterAccent` → `_SCCenterAccent`, `2017`). Buildability tests: `SFIsCompositBuildable` (`1244`), `SFIsSomethingBuildable` (`1354`), `hascomposing` (`1321`), `SFIsRotatable` (`1285`).
- **Placement heuristics** (`_SCCenterAccent`, `2017-2267`) in priority order: (1) if the previous reference and this accent share a **mark-to-mark or cursive anchor class** (`AnchorClassMkMkMatch`, `1932`; `AnchorClassCursMatch`, `1949`), stack relative to it; (2) if base and accent share a **mark anchor class** (`AnchorClassMatch`, `1914`), use `ap1.me - ap2.me` — i.e. real anchors win; (3) otherwise geometry: pick a *reference base* (if the base is itself composite, use its base — e.g. accents on `Uhorn` center on `U`, `2036-2039`; `Ø/ø → O/o`, `2043-2044`), find slanted bounds (`SplineCharFindSlantedBounds`, `1529`, italic-angle aware), then apply per-accent special cases — cedilla/ogonek (0x327/0x328) and ypogegrammeni (0x345) use the accent's *top* bounds with a 1/30 overlap (`2045-2051`); grave/acute/hungarumlaut/hook optionally use *bottom* bounds; `Aring` gets 1/30 overlap (`2054-2056`). Then it establishes a "common accent line" across a/e/o vs i/u so accents sit at consistent heights (comment at `2094-2100`), applies `accent_offset` (default 6 % of em, `fvcomposite.c:48`), and does optical X placement using `SCFindTopXRange`/`SCFindBottomXRange` (`1468`/`1483`) and stem detection (`SCStemCheck`, `1548`).
- Other builders: `SCPutRefAfter` (`2302`) for spacing accents, `DoSpaces` (`2370`), `DoRules` (`2467`), `DoRotation` (`2554`, vertical forms), `SCBuildHangul` (`2670`), `SCMakeDotless` (`2742`), `SCMakeRightToLeftLig` (`2639`), `SCSetReasonableLBearing` (`2772`). Bitmap parallels exist for every one (`BCAddReference`, `_BCCenterAccent`, `BCMakeSpace`, …). `SCBuildComposit` (`2813`) is the driver; `SCAppendAccent` (`2911`) the incremental API.
- **Weaknesses.** Latin/Greek/Cyrillic-centric; the accent synonym tables (`accents[][4]`, `fvcomposite.c:60-130`) and name tables (`uc_accent_names`, `159`) are hand-maintained. Depends on a bundled Unicode decomposition table rather than a live UCD.
- **Rust option.** `unicode-normalization` gives you NFD for free. The placement heuristics have no equivalent.
- **Recommendation. Port the heuristics; replace the Unicode layer.** Use `unicode-normalization` + `unicode-properties` for decomposition and combining classes (FontForge's `pose()` / combining-class overrides in `utype.h` map onto `Canonical_Combining_Class`). The anchor-first, geometry-fallback priority and the specific accent special-cases are hard-won and should be ported faithfully — they're only ~250 lines of real logic inside `_SCCenterAccent`.

## `glyphcomp.c` (2372 lines)

- **Approach.** Outline comparison at three levels: `ContourPointsMatch` (`332`, exact point-by-point), `ContourMatch` (`221`, geometric — samples one contour and checks each sample lies within `err` of the other via `NearSplineSet`, `114`, with `FindNewT`, `95`, doing local Newton refinement), and `SSsCompare` (`348`) which pairs contours and returns an `enum Compare_Ret` bitmask. Also `SSRefCompare` (`465`), `RefCheck` (`600`), `BitmapCompare` (`520`, with pixel-error and bounding-box-error tolerances), `CompareHints` (`711`), `CompareGlyphs` (`837`, the scripting entry point taking `pt_err` and `spline_err`). Font-level diffing is `comparefontglyphs` (`1198`) driven by `struct font_diff`, with HTML/text reporting (`GlyphDiffSCError`, `944`) and the ability to paste the other font's outline into the background for visual diff (`SCAddBackgrounds`, `1063`).
- **Weaknesses.** Contour pairing is greedy; comparison is not invariant to start-point choice unless `ContourMatch`'s sampling path is used.
- **Rust option.** None directly. `kurbo` gives you the sampling and nearest-point primitives.
- **Recommendation. Port** — it's small, self-contained, and a font editor needs it (regression tests, "compare fonts", interpolation-compatibility checks). Modernise: pair contours by area+centroid signature rather than greedily.

## `spiro.c` (302 lines)

- **Approach.** A thin adapter over **libspiro** (Raph Levien's clothoid/Euler-spiral curves). `SplineSet2SpiroCP` (`51`/`167`) converts FF points to `spiro_cp[]` using the point's `ttfindex`-adjacent `spiro_index`; `SpiroCP2SplineSet` (`47`/`154`) runs libspiro and receives cubic segments through a bezier context (`bezctx_ff.c`). `SSRegenerateFromSpiros` (`278`) re-runs the solve after an edit. `hasspiro`/`libspiro_version` (`236`/`240`) gate the feature; the file is compiled twice — with and without `_NO_LIBSPIRO` (note the duplicate definitions at `43`/`69` and `47`/`154`). Spiro points live alongside the Bézier representation: `SplineSet.spiros`, `spiro_cnt`, `spiro_max`, and `sc->inspiro`.
- **Weaknesses.** The spiro representation is the source of truth only while `inspiro` is set; every operation must remember to regenerate or the two go out of sync. Conversion is lossy in one direction.
- **Rust option.** `kurbo` has `SpiroCurve`-adjacent work but the canonical Rust port is **`spiro-rs`** / Levien's own `spiro` crate; alternatively bind `libspiro` via FFI. `kurbo::euler` (Euler spiral / "parallel curve" work) is closely related.
- **Recommendation. Use crate (or FFI to libspiro).** Do not port the solver. Do port the *dual-representation bookkeeping* discipline — but design it better: make the spiro CP list the authoritative layer representation when in spiro mode, with the Bézier layer a derived cache, rather than FontForge's "both are live" model.

## `splinefill.c` (1823 lines) + `freetype.c` (1155 lines)

- **`splinefill.c` approach.** A classic **active-edge-list scanline rasterizer**. `AddSpline` (`322`)/`AddEdge` (`177`) break each spline at extrema into monotone `Edge`s bucketed by scanline; `ActiveEdgesRefigure` (`464`) advances the AEL per scanline (using `TOfNextMajor`, `81`, to step `t` rather than recomputing); `FillChar` (`567`) fills between edge pairs. It is **hint-aware**: `InitializeHints` (`628`) records hstems that fail to cross a pixel boundary and nudges them, and `isvstem` (`552`) snaps span endpoints to vstem positions inside `FillChar` (`586-596`) — this is a poor man's grid-fitting so unhinted FontForge output still looks reasonable. There is also a "dropout-ish" continuity fix between adjacent scanlines (`598-616`). Type 3 / multi-layer glyphs go through a bytemap path with per-layer fill/stroke/gradient/pattern (`ProcessLayer`, `1276`; `StrokePaths`, `1024`; `GradientHere`, `1077`; `PatternPrep`, `1147`; `FillImages`, `1213`), and stroked fonts through `StrokeGlyph` (`1015`) with `Bresenham` (`836`). Anti-aliasing is **supersampling**: `SplineCharAntiAlias` (`1582`) rasterizes at `pixelsize * linear_scale` (typically 4) and downsamples (`BCTruncateToDepth`, and `ByteMult(…,17)` at `1697` to convert 4-bit to 8-bit).
- **`freetype.c` approach.** `__FreeTypeFontContext` (`162`) generates an in-memory font (TTF or CFF) from the current `SplineFont` — optionally with only the glyphs in a transitive closure of references (`TransitiveClosureAdd`, `122`) — and loads it with FreeType. Then: `SplineCharFreeTypeRasterize` (`431`)/`SplineFontFreeTypeRasterize` (`460`) produce `BDFChar`s from `FT_Bitmap` (`BdfCFromBitmap`, `378`), and `FreeType_GridFitChar` (`635`) converts the *grid-fitted outline* back into a `SplineSet` via `FT_Outline_Decompose` with `FT_MoveTo/LineTo/ConicTo/CubicTo` callbacks (`540`-`634`) — this is what draws the grid-fit preview in the char view. `FreeType_GetRaster` (`691`) returns the raster for the debugger. `FillOutline` (`729`) is the reverse direction (SplineSet → `FT_Outline`) used for the non-font-generating path, with `LayerAllOutlines`/`StrokeOutline`/`RStrokeOutline` (`837`/`861`/`898`) flattening type-3 layers. Capability probes: `hasFreeType`, `hasFreeTypeByteCode`, `hasFreeTypeDebugger` (`47`/`68`/`89`).
- **Weaknesses.** The internal rasterizer's quality is well below FreeType's or a modern analytic-coverage rasterizer; the "hint-aware span snapping" is a hack. Round-tripping through a generated font file for every FreeType operation is expensive.
- **Rust option.** Rasterization: `tiny-skia`, `zeno`, `swash`'s scaler, `ab_glyph`/`fontdue` rasterizers, or `vello` on GPU — all better than `splinefill.c`. Grid-fitting: **`skrifa`** (fontations) now has a full TrueType hinting interpreter in safe Rust, so you can grid-fit and get outlines back *without* FreeType and without writing a font file. `freetype-sys`/`freetype-rs` remain available.
- **Recommendation. Use crates.** Replace `splinefill.c`'s outline rasterizer with `tiny-skia` or `zeno` (analytic AA, correct, fast). Replace `freetype.c` entirely with **`skrifa`** for hinted rasterization and grid-fit preview — it eliminates the "serialize a font to feed the rasterizer" round trip, which is a significant architecture win. Keep FreeType behind an optional feature only for the bytecode *debugger* (below). Do **port** the type-3/multi-layer compositing logic if you intend to support type-3 fonts; nothing else does it.

## `bitmapchar.c` (984) / `bvedit.c` (967)

- **Approach.** `BDFChar` (`splinechar.h:~280-306`) is a bitmap with `xmin/xmax/ymin/ymax`, `bytes_per_line`, `depth`, `byte_data`, a `selection`/`backup` `BDFFloat` (floating selection), `dependents`, and `BDFRefChar` references. `bvedit.c` provides the editing ops: `BCTransFunc` (`57`, flip/rotate/skew/shift via `enum bvtools`), `BCTrans` (`233`), `BCSetPoint` (`343`), `BCExpandBitmap`/`BCExpandBitmapToEmBox` (`273`/`328`), floating-selection ops (`BDFFloatCreate` 419, `BDFFloatConvert` 378, `BCFlattenFloat` 481), `BCPasteInto` (`513`), reference handling (`BCMergeReferences` 546, `BDFGetMergedChar` 555, `BCPrepareForOutput` 652, `BCMakeDependent` 721, `BCUnlinkThisReference` 762), and scaling (`BCScale` 793, `BCScaleGrey` 859, `BitmapFontScaleTo` 936). `bitmapchar.c` is mostly BDF property/XLFD machinery (`XLFD_GetComponents` 531, `XLFD_CreateComponents` 566, `Default_Properties` 654, `BDFDefaultProps` 821) plus `BDFMakeGID`/`BDFMakeChar` (`842`/`895`).
- **Strike regeneration** is in `bitmapcontrol.c`: `BitmapControl` (`343`) → `BitmapsDoIt` (`314`) → `FVRegenBitmaps` (`216`)/`FVRemoveBitmaps` (`278`), with `SFFigureBitmaps` (`106`), `FVScaleBitmaps` (`147`, scale from an existing strike instead of re-rasterizing) and `ReplaceBDFC` (`177`). Rasterization source is chosen per-strike by flags on `BDFFont`: `freetype_context`, `recontext_freetype`, `unhinted_freetype`, `clut` — see `BDFPieceMeal` (`splinefill.c:1661-1701`), which tries hinted FreeType, then per-glyph FreeType, then unhinted FreeType, then the internal AA rasterizer, then the internal mono rasterizer. Display fonts are lazily rasterized per glyph (`BDFPieceMealCheck`, `1704`; `SplineFontPieceMeal`, `1718`).
- **Tracking outline changes:** there is no dependency graph — `sc->changedsincelasthinted`-style tracking exists for hints but strikes are only refreshed when the user runs Regenerate Bitmaps, or lazily for piecemeal display fonts (which are discarded and rebuilt on change).
- **Weaknesses.** Bit-packing is hand-rolled everywhere; `depth` vs `byte_data` vs `bytes_per_line` semantics differ per depth and are a frequent bug source. No proper invalidation.
- **Rust option.** No bitmap-font-editing crate exists. `image` handles the pixel container.
- **Recommendation. Rewrite the data structure, port the operations.** Use a single `Bitmap { w, h, origin, depth, data: Vec<u8> }` with depth-generic accessors instead of FontForge's `bytes_per_line`/`byte_data` split. Port `BCTransFunc`, `BCScale`/`BCScaleGrey` and the floating-selection model — those are real algorithms. Add a proper dirty-tracking layer (outline generation counter per glyph) so strikes can be invalidated automatically; FontForge's lack of this is a genuine defect.

## `ttfinstrs.c` + the debugger

- **Approach.** `ttfinstrs.c` is a 1:1 assembler/disassembler: a 256-entry mnemonic table (`instrs[]`, ending at `~294`) with the decorated names (`MIRP[rp0,min,rnd,black]` etc.), `_IVParse` (`296`) assembling text → bytes with push-run coalescing (`push_left`/`push_size`, NPUSHB/NPUSHW/PUSHB/PUSHW selection), `instr_typify` (`490`) classifying each byte as opcode/operand for the UI, and `_IVUnParseInstrs`/`__IVUnParseInstrs` (`563`/`537`) for disassembly.
- The **debugger** is not in `fontforge/` at all — it's `fontforgeexe/freetypeui.c` (`DebuggerCreate` `383`, `DebuggerGo` `435`, `DebuggerReset` `345`, `DebuggerTerminate` `317`, breakpoints `DebuggerBpCheck`/`ToggleBp` `479`/`489`, watches `DebuggerSetWatches` `515`) driving FreeType's `TT_ExecContext` through a hooked `TT_RunIns` (note the `massive_kludge` global at `185`). Requires FreeType built with `TT_CONFIG_OPTION_BYTECODE_INTERPRETER` and the internal-header hack (`hasFreeTypeDebugger`, `freetype.c:89`).
- **Weaknesses.** The debugger depends on FreeType *internal* headers — historically the most fragile part of the FontForge build.
- **Rust option.** Assembler/disassembler: `ttf-parser` doesn't do it; `fonttools`' `ttProgram` is the reference. **`skrifa`'s** hinting engine (`skrifa::outline::HintingInstance`) is a full, safe TrueType interpreter — and unlike FreeType it is a normal library you can step, because you control the source.
- **Recommendation. Port the assembler/disassembler (small, mechanical); build the debugger on `skrifa` instead of FreeType.** The opcode table is ~300 lines of data. For the debugger, `skrifa`'s interpreter would need a stepping/instrumentation hook — that's a fork or an upstream feature request, but it is far more tractable than depending on FreeType internal headers, and it removes the hardest build dependency FontForge has.

## `search.c` (1492 lines)

- **Approach.** Outline find/replace. A `SearchData` holds the pattern contours and match flags `enum search_flags {sv_reverse, sv_flips, sv_rotate, sv_scale, sv_endpoints}` (`baseviews.h:~431`). Matching walks the glyph's points looking for a start correspondence (`SPMatchesF`, `68`; `SPMatchesO`, `456`; `SPMatches`, `554`) under a candidate similarity transform which is progressively refined (`SVBuildTrans`, `526`; `SVFigureTranslation`, `543`); `CoordMatches`/`BPMatches` (`42`/`49`) apply the fuzz. Two modes: `SCMatchesIncomplete` (`579`, pattern is an open path matched as a sub-path) and `SCMatchesFull` (`610`, whole contour). Replacement splices in the replacement path (`RplInsertSP`, `732`; `DoReplaceIncomplete`, `791`; `DoReplaceFull`, `929`) with `FudgeFigure` (`760`) distributing the residual error and `AdjustBP`/`AdjustAll` (`702`/`720`) fixing control points. `HeuristiclyBadMatch` (`902`) rejects degenerate matches. Drivers: `SearchChar` (`1082`), `DoRpl` (`1099`), `_DoFindAll` (`1122`).
- **Weaknesses.** O(points²) per glyph; brittle under scaling; the "fudge" redistribution can produce non-smooth joins.
- **Rust option.** None.
- **Recommendation. Port** — it's a distinctive feature with no substitute, and 1500 lines is tractable. Improve the candidate-start search with a rotation-invariant shape signature to cut the quadratic factor.

## `ikarus.c` / `autotrace.c` (image → outline)

- **`ikarus.c`** (861 lines) is an *importer* for the URW Ikarus format, not a tracer: `SFReadIkarus` (`599`), `IkarusReadChar` (`448`), `IkarusAddContour` (`416`) which converts Ikarus's start/corner/curve point classification into Béziers, plus a URW glyph-number → name table (`InitURWTable`, `50`; `IkarusNameFromURWNumber`, `390`).
- **`autotrace.c`** (832 lines) shells out to the external `autotrace` or `potrace` binaries (`_SCAutoTrace`, `235`/`329`; `FindAutoTraceName`, `619`; the choice is made by `strstrmatch(prog,"potrace")`, `254`/`350`). ## `cvundoes.c` (3903 lines)

- **Approach.** Undo is **per-layer**, not per-glyph: `AddUndo(undo, &layer->undoes, &layer->redoes)` (`cvundoes.c:581`), reached via `CVAddUndo` (`610`) which indexes `cv->layerheads[cv->drawmode]`. `maxundoes` defaults to **120** (`cvundoes.c:77`, exposed as the `UndoDepth` preference at `noprefs.c:204`); `-1` means infinite, `0` disables undo entirely (used for scripting — every `*PreserveState` early-returns on `no_windowing_ui || maxundoes==0`, e.g. `632`, `675`, `740`). Trimming walks the list to `maxundoes` and frees the tail (`588-603`). Pushing an undo always clears the redo stack (`584-585`).
- **What's copied.** `Undoes` (`splinechar.h:359-406`) is a tagged union over `enum undotype` (`splinechar.h:308-327`): `ut_state` (splines, refs, images, anchors, width, vwidth, lbearing change, fill brush / stroke pen / dofill / dostroke / fillfirst), `ut_statehint` (adds hints + `ttf_instrs`), `ut_statename` (adds unicode, charname, comment, possub), `ut_statelookup`, `ut_anchors`, `ut_width`/`ut_vwidth`/`ut_lbearing`/`ut_rbearing`, `ut_possub`, `ut_hints`, `ut_bitmap`/`ut_bitmapsel` (a whole embedded `BDFChar`), `ut_composit` (an outline state + a list of bitmap states), `ut_multiple`/`ut_layers` (a list of sub-undoes, one per layer). Each record also stores `was_modified`, `was_order2`, `layer`, and `copied_from` (the source `SplineFont`, so cross-font paste can be detected). It is a **deep copy**: `SplinePointListCopy`, `RefCharsCopyState` (`86`), `ImageListCopy`, `AnchorPointsCopy`, `UHintCopy` (`423`). There is no structural sharing and no diffing.
- Restoration does non-trivial fixup: `FixupRefChars` (`203`) re-links references by identity where possible (`RefCharInList`, `175`; `RefCharsMatch`, `137`), `FixupImages` (`348`), `FixupBDFRefChars` (`294`), `ExtractHints` (`460`). `UndoesFreeButRetainFirstN` (`501`) supports partial trimming. Hint undoes are gated by a separate `preserve_hint_undoes` flag (`cvundoes.c:~681`).
- **Weaknesses.** Full deep copy per operation — expensive on large glyphs and pathological on scripted batch operations (hence the `maxundoes==0` escape hatch, which means *scripts get no undo at all*). Per-layer stacks make cross-layer operations awkward (`ut_layers` is the workaround). `copied_from` as a raw pointer is a use-after-free waiting to happen when the source font closes.
- **Rust option.** `im`/`rpds` (persistent data structures), or an event-sourced command model.
- **Recommendation. Do not port the model; port the *inventory*.** The valuable artefact here is the exhaustive list of what constitutes "glyph state" (the `Undoes` union) — reproduce that faithfully. But implement it as **immutable layer snapshots with structural sharing** (`Arc<Layer>` + persistent contour lists) or a command/inverse-command log. That makes undo O(1)-ish, works for scripts, and removes the `maxundoes==0` compromise. Keep the per-layer granularity as a UI concept but back it with a single font-level undo timeline so cross-layer and cross-glyph operations are atomic.

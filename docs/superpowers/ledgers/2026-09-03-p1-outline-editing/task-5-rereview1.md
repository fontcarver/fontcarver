### New Breakage in the Fix Diff

1. **Minor — `WorkerGuard` can clear a successor worker's flag, so "at most one worker per entry" is no longer an invariant.** `crates/fw-layout/src/shaping.rs:489-504` sets `state.worker = false` under the lock and returns; the guard (`:449-455`) then takes the lock a second time and clears `worker`/`building` unconditionally. A `schedule` (`:346-360`) that slips between those two lock acquisitions sees `worker == false`, spawns a new worker and sets `worker = true` — which the exiting worker's guard immediately clobbers back to `false`. From then on `scheduled_for` (`:414-421`) is false for every generation, so the next `plan` returns `Rebuild`, the handler clones the font again and spawns a *second* live worker. The old code cleared the flag only under the lock in the loop body, which is why the previous review could call the handshake race-free. Window is a few instructions and the state self-heals on the next shape request; a worker token (or clearing only when the guard still owns the flag) would restore the invariant.
2. **Minor — publishing is not generation-monotone, so an older compile can land over a newer one.** `crates/fw-layout/src/shaping.rs:520` and `:254` assign `state.compiled` unconditionally. With two live workers (breakage 1) or with two concurrent first-ever shapes at different generations (`PlanKind::First` no longer holds the entry lock across the compile, unlike the old `compiled_font`), the slower compile overwrites the newer font. `stale` is still reported truthfully afterwards and the next `plan` reschedules, so this is transient; guarding both assignments with `compiled.generation > existing.generation` would close it.
3. **Minor — `plan` → clone → `schedule` is check-then-act across callers.** `crates/fw-api/src/handlers/shaping.rs:47-48` decides `needs_font()` and clones under the session read lock, but nothing is reserved on the entry until `schedule` runs (`crates/fw-layout/src/shaping.rs:346`). Two concurrent `text.shape` calls at the same stale generation therefore each clone the whole `Font` (one of the two clones is dropped inside `schedule`), and two concurrent first-ever shapes each run a full synchronous compile. Ruling 1's "clone only when a rebuild is actually going to be scheduled" holds per caller, not across callers.
4. **Minor — `a_shaping_compile_does_not_block_document_edits` is wall-clock in both directions.** `crates/fw-api/tests/shaping.rs:203-217`: the lower bound (`compile > 500 ms`) is safe — a 6 000-glyph fontc compile will not drop under half a second — but the upper bound (`edit < 500 ms`, plus `edit * 10 < compile`) is a single write-lock acquisition timed while a multi-threaded fontc compile saturates the machine and the rest of the workspace suite runs in parallel. It is the round's most flake-prone assertion. A structural form would be strictly better: record the shaping thread's compile start/end instants and assert the edit's completion instant falls inside that window, dropping the absolute 500 ms bound.
5. **Minor — `widths_for_text` scans the whole glyph map under the session read lock.** `crates/fw-layout/src/shaping.rs:369-385` iterates every glyph and every `unicodes` entry on every shape request; for a 65 k-glyph CJK document that is a linear scan holding the read lock a writer must wait behind. Check I ran: `fw-model` exposes no reverse cmap (`grep` for `glyph_for_unicode|unicode_map|by_unicode` in `crates/fw-model/src` finds nothing) and `fw-model` is off-limits this round, so the scan is the only available shape — but it is new work under the lock that the previous design did not do.
6. **Minor — `recovered_from` is never cleared by `session.save`.** `crates/fw-api/src/handlers/session.rs:145-152` inserts the marker and only `session.close` (`:60-64`) removes it, so a recovered document that has been saved over its original path still reports `recovered_from` and a UI banner driven by the field would stay up for the rest of the session.
7. **Minor — `FAILED_STAGE` is unreachable for consumers.** `crates/fw-api/src/api.rs:28` declares `pub const FAILED_STAGE` inside a private module (`crates/fw-api/src/lib.rs:5`, `:10` re-exports only `Api` and `METHODS`), so the stable stage name a UI must match on is effectively a documented string literal, unlike `fw_layout::COMPILE_FAILED`, which is re-exported.

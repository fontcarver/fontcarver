### New Breakage in the Fix Diff

1. **Minor — `WorkerGuard` can clear a successor worker's flag, so "at most one worker per entry" is no longer an invariant.** `crates/fw-layout/src/shaping.rs:489-504` sets `state.worker = false` under the lock and returns; the guard (`:449-455`) then takes the lock a *second* time and clears `worker`/`building` unconditionally. A `schedule` (`:331-344`) that slips between those two acquisitions sees `worker == false`, spawns a fresh worker and sets `worker = true` — which the exiting worker's guard immediately clobbers back to `false`. From then on `scheduled_for` (`:414-421`) is false for every generation, so the next `plan` returns `Rebuild`, the handler clones the font again and `schedule` spawns a *second* live worker. The old code cleared the flag only inside the locked loop body, which is why the previous review could call the handshake race-free. The window is a few instructions and the state self-heals on the next shape request; a worker token (clear only while the guard still owns the flag) would restore the invariant.
2. **Minor — publishing is not generation-monotone, so an older compile can land over a newer one.** `crates/fw-layout/src/shaping.rs:520` and `:254` assign `state.compiled` unconditionally. With two live workers (breakage 1), or with two concurrent first-ever shapes at different generations — `PlanKind::First` (`:248-258`) no longer holds the entry lock across the compile, unlike the old `compiled_font` — the slower compile overwrites the newer font. `stale` is still reported truthfully afterwards and the next `plan` reschedules, so the regression is transient; guarding both assignments with `compiled.generation > existing.generation` would close it.
3. **Minor — `plan` → clone → `schedule` is check-then-act across callers.** `crates/fw-api/src/handlers/shaping.rs:47-48` decides `needs_font()` and clones under the session read lock, but nothing is reserved on the entry until `schedule` runs (`crates/fw-layout/src/shaping.rs:331`). Two concurrent `text.shape` calls at the same stale generation each clone the whole `Font` (one clone is dropped inside `schedule`), and two concurrent first-ever shapes each run a full synchronous compile. Ruling 1's "clone only when a rebuild is actually going to be scheduled" holds per caller, not across callers.
4. **Minor — `a_shaping_compile_does_not_block_document_edits` is wall-clock in both directions.** `crates/fw-api/tests/shaping.rs:210-218`: the lower bound (`compile > 500 ms`) is safe — a 6 000-glyph fontc compile will not fall under half a second on plausible hardware — but the upper bound (`edit < 500 ms`, with `edit * 10 < compile`) times a single write-lock acquisition while a multi-threaded fontc compile saturates the machine and the rest of the workspace suite runs in parallel; it is the round's most flake-prone assertion. A structural form would be strictly better: record the shaping thread's compile start/end instants, assert the edit's completion instant falls inside that window, and drop the absolute 500 ms bound.
5. **Minor — `widths_for_text` scans the whole glyph map under the session read lock.** `crates/fw-layout/src/shaping.rs:369-385` iterates every glyph and every `unicodes` entry on every shape request; for a 65 k-glyph CJK document that is a linear scan a writer must queue behind. Check I ran: `fw-model` exposes no reverse cmap (`grep -rn "glyph_for_unicode|unicode_map|by_unicode" crates/fw-model/src` finds nothing) and `fw-model` is off-limits this round, so the scan is the only shape available — but it is new work under the lock that the previous design did not do.
6. **Minor — `recovered_from` is never cleared by `session.save`.** `crates/fw-api/src/handlers/session.rs:145-152` inserts the marker and only `session.close` (`:61-64`) removes it, so a recovered document that has already been saved over its original path keeps reporting `recovered_from`, and a UI banner driven by the field stays up for the rest of the session.
7. **Minor — `FAILED_STAGE` is unreachable for consumers.** `crates/fw-api/src/api.rs:28` declares `pub const FAILED_STAGE` inside a private module (`crates/fw-api/src/lib.rs:5` `mod api;`, `:10` re-exports only `Api` and `METHODS`), so the stage name a UI must match on is effectively a documented literal — unlike `fw_layout::COMPILE_FAILED`, which is re-exported.

### New Breakage in the Fix Diff

**Minor — `NumberField`'s clamp lets a value below `min` through when no `max` is given, losing the grid-size guard the old code had.** `app/src/dialogs/NumberField.tsx:42`: `Math.min(max ?? parsed, Math.max(min ?? parsed, parsed))` — the outer `Math.min` falls back to the *raw* `parsed`, not to the already-min-clamped value, so for `min = 0, max = undefined, parsed = -5` it returns `-5` (verified by evaluating the expression). That is exactly the shape of grid size (`PreferencesDialog.tsx:195-198`, `min={0}`, no max) and all three nudge steps (`:176-178`); autosave is safe because it has `max={3600}`. Typing `-5` into a `type="number"` box with `min=0` is possible (the value is only :invalid, still readable), so `update({ grid_size: -5 })` reaches `prefs.set`, and neither `prefsStore.persist` nor the kernel validates: `grid_size` and `nudge` are `f64` and `handlers::prefs::set` writes the record verbatim (`crates/fw-api/src/types/session.rs:200-208`, `crates/fw-api/src/handlers/prefs.rs:23-30`). The previous code clamped grid size with `Math.max(0, …)`, so this is a regression of an existing guard (nudge was already unclamped). One-line fix: `Math.min(max ?? Infinity, Math.max(min ?? -Infinity, parsed))`.

**Minor — `prefsStore.update` can still lose a patch when two updates race before the load resolves, and issues one `prefs.get` per racing update.** `prefsStore.ts:102-108` calls `get().load()` without de-duplicating an in-flight read. With two updates started while `loaded` is false: the first read resolves, update A persists `{stored, patchA}` (setting the store synchronously at `:65`), then the second read resolves and `load` overwrites the store with the bare `stored` record (`:84`), so update B computes `{...stored, patchB}` and its `prefs.set` lands last on disk without `patchA`. Single-update paths are correct, and `AppShell.tsx:62` loads at start-up so the window is narrow (it needs two preference writes inside one outstanding read — e.g. a View-menu theme click plus a dialog field while the start-up read is still in flight, or after a failed start-up read). A memoised in-flight `load` promise, or serialising writes, closes it. The double `prefs.get` (`PreferencesDialog.tsx:45` also loads on mount) is harmless but redundant.

**Nit — the chrome test reads the first matching rule in the stylesheet.** `Dialog.test.tsx:36-40` matches `.dialogHeader[^{}]*\{…\}` against the file text, which resolves to the unscoped P0 rule only because it appears earlier in `dialog.module.css`; reordering the file would silently make the assertions test the wrong rule. It does verify the right numbers today.
